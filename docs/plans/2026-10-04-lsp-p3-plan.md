# LSP P3 实施计划

> 接续 [2026-10-04-lsp-manager-plan.md](2026-10-04-lsp-manager-plan.md)（P0–P2 已完成并合入 main）。任务编号从 T18 接着排，步骤用 `- [ ]` 跟踪。

**Goal:** 补上 P0 留下的诊断缺口，给 agent 一个安全的跨文件 `RenameSymbol`，让 Python 开箱可用，开放用户和插件两种配置来源，并在桌面文件查看器里标出诊断。

**测试命令：** `bash scripts/with-project-node.sh pnpm --filter @zclaudia/server test -- <files>`；桌面端 `pnpm --filter @zclaudia/desktop test -- <files>`；e2e 见 `e2e/tests/agent-runtimes/lsp.playwright.spec.ts`。

## 已定决策（2026-10-04）

1. **配置来源：用户级自定义 + 插件 `contributes.lspServers`，项目文件暂缓。**
   - 用户在设置里填写的命令等同于自己在终端执行，不另做信任确认（与 MCP 服务器配置同级）。
   - 插件声明的服务器要求该插件已获得 `shell.execute`，并且**每次启动时重新检查**，撤销后立即生效。未授权时不在运行中途弹窗，而是在设置页和指示器里显示 "Needs permission"，并提供 Allow 按钮。
   - 优先级：用户 > 插件 > 内置。id 相同视为覆盖，同一扩展名由优先级高的认领。
   - `.zclaudia/lsp.json` 暂缓。以后要做，也只做"只能配置已可信的服务器、不能定义命令"的版本，从而绕开工作区信任问题。
2. **托管安装：这期只做缺失提示，并随包附带 pyright。**
   - 项目里有根标记文件，但找不到可执行文件时，显示 "Not installed"，并给出安装命令。这只是给用户看的提示，不是下载元数据，不违反 `docs/managed-runtimes.md:87`。
   - pyright 与 TypeScript 一样随包发布（npm 包解压后约 19.5MB，MIT），同时要解决 venv 识别。
   - rust-analyzer 托管下载推迟到"插件托管安装"单独立项（需要：从 `agentRuntimes` 解耦、支持 `.gz`、加进度事件、修复发布者校验）。
3. **rename：单独的 `RenameSymbol` 工具，全部成功或全部不写。**
   - 加入 `EDIT_TOOLS`，不作为 LSPTool 的 action（LSPTool 属于只读工具，plan 模式会放行）。
   - 调用前对锚点文件按 `fileWrite` 征询；执行中逐路径硬检查，工作区外、依赖库里或敏感文件一律整体拒绝，不在中途弹窗。
   - 不要求先 Read：持锁后比对磁盘哈希与语言服务器所用版本，任何一个对不上就中止。写完后更新已读快照。
   - 内存预计算 → 多文件锁 → 写入 → 失败时用内存原文回滚。每个文件仍调用 `recordFileBackup`。
   - 只接受文本编辑：声明 `resourceOperations: []`，先调用 `prepareRename`。默认直接应用，提供 `preview_only`。
4. **桌面端：主查看器做被动显示 + 手动启动。**
   - 该项目的服务器正在运行就显示诊断；头部提供 "Check types" 按钮，点击后查看器在打开期间持有租约。
   - 标记只做行号圆点、整行底色、悬停弹窗和头部统计。不做波浪线、悬停类型或跳转。
   - 新接口只接受已登记的项目根目录或会话 worktree，因为启动 TS 服务器会执行项目里的 `typescript`。

## 核实结论（决定改法）

- **补丁模式的诊断，模型看不到。** Edit `patch` 模式逐文件调用 `createEditBridgeTool`，诊断留在 `perFileResults[i].lifecycle`，但 `formatPerFileResults`（`edit-write/mutation-details.ts:116`）不输出它。顶层结果没有 `lifecycle`，桌面端 `FileMutationResult` 的 `perFileResults` 也只渲染 diff。
- **预设表是固定的。** `LanguageServerManager` 构造时拿到 `presets` 数组（`manager.ts:148`），`presetForFile` 按扩展名取第一个匹配（`manager.ts:543`）。任何新来源都要先改成动态注册表。
- **服务器拉取配置时，客户端一律回 `null`。** `client.ts:104` 对 `workspace/configuration` 的每一项都返回 `null`。pyright 的 venv 和规则覆盖都要靠这个请求下发，所以预设要能提供 settings。
- **路径类权限检查只看顶层 `file_path`。** `extractFilePath`（`permission-evaluator.ts:94`）、`isSensitiveFile`（:309）、`getOutsideWorkspacePaths`（:191）在 application 层；`RenameSymbol` 在 infra 层，按分层规则不能反向引用，`isSensitiveFile` 要下沉到 utils 层共用。
- **可复用的写入步骤。** edit-tool 在算出新内容之后的那段（:1056-1143：内容校验、备份、原子写、`recordWrite`、diff、生命周期钩子）还没有抽成函数。`runWithFileWriteLocks`（`edit-write/shared.ts:299`）按排序加多文件锁，可以直接用。
- **插件权限。** `PermissionManager.hasPermission(pluginId, permission)`（`application/plugins/permissions.ts:82`）可以随时查询；授权和撤销路由 `POST /api/plugins/:id/permissions/grant|revoke` 已经存在，但桌面端从未调用。插件目录是 `instance.path`；相对路径解析及防逃逸的写法参考 skills（`loader.ts:1045`）。
- **查看器。** `FileViewerPanel` 用 prism-react-renderer + react-window，每行由 `CodeRow` 渲染，行号栏只是 `<span>`。store 里有 `projectRoot` 和 `targetLine`（`fileViewerStore.ts:14,27`），可以用来校验根目录和跳转到下一处。
- **随包方式。** `server/scripts/bundle.mjs:357` 已有把 `typescript-language-server` 复制到 `bundle/vendor/` 的先例。pyright 的入口是 `langserver.index.js`，`engines.node >= 14`，用 sidecar node 启动。

## P3a：诊断补洞 + 缺失提示

- [x] **T18 多文件诊断汇总。**
  - 新增 `aggregateDiagnosticsReports(perFile)`：合并为一个报告，每条错误带文件路径，按文件分组，总数上限 10 条，保留 "not checked" 状态（任一文件 pending 就注明哪些文件没查）。
  - patch 模式成功和部分失败的结果文本都输出汇总；顶层 `details.lifecycle` 也带上汇总，供界面显示。
  - 桌面端 `FileMutationResult` 在多文件结果里显示汇总后的诊断。
- [x] **T19 其他已打开文件的新增错误（先实测）。**
  - 先实测：typescript-language-server 在一个文件 `didChange` 之后，会不会重新推送**其他已打开文件**的诊断，延迟多少。
  - 如果会：写入后，对同一服务器里其他已打开的文件，以它们写入前的稳定诊断为基线，报告新增错误，放在 "Other open files" 小节。总预算不额外增加（复用 3s），超时的文件不报。
  - 结果文本注明：只检查了已打开的文件，没打开的调用方不在检查范围内。
  - 如果不会：记录结论，本任务取消，在风险里注明。
- [x] **T20 缺失提示。**
  - 预设增加 `installHint?: string`，并把"项目是否适用"（有根标记文件）和"能否启动"（找得到可执行文件）分开。
  - `LanguageServerState` 增加 `missing`，状态条目带 `installHint`。`status()` / `statusFor()` 列出 missing，`serversFor` 仍然排除它。
  - 提示内容：rust-analyzer 是 `rustup component add rust-analyzer`，gopls 是 `go install golang.org/x/tools/gopls@latest`。pyright 随包后不再缺失（见 P3b）。
  - rustup 代理存在但组件没装（启动即退出）的 failed 条目也附上同一条提示。
  - 桌面端：指示器弹窗和设置页显示 "Not installed" 和一条可复制的命令，状态点用中性色。打开设置页时强制重新探测，绕过 60s 缓存。
  - 只有 missing 的服务器时，指示器仍然显示，但用中性点，不做成警告。

**P3a 验收：** 用 patch 一次改两个 TS 文件并各引入一个错误，模型收到的结果里两个错误都在；在只有 `Cargo.toml`、没装 rust-analyzer 的项目里，指示器弹窗显示 "Not installed" 和安装命令。

**P3a 实施记录（2026-10-04，分支 `feat/lsp-p3a`）：**

- **实测发现 P0 的一个缺陷（已修复）：** typescript-language-server 在某个文件的诊断从空变成空时不发布（`FileDiagnostics.update` 直接跳过）。于是最常见的情况——干净文件改完仍然干净——永远等不到推送，写后诊断白等满整个预算（生产 3s），再告诉模型 "not checked, did not answer in time"。用真服务器复现过：去掉修复后，干净编辑耗时正好等于预算。
- **修法：按需拉取诊断。** 预设新增可选的 `pullDiagnostics`。TypeScript 通过 typescript-language-server 的 `typescript.tsserverRequest` 命令调用 tsserver 的 `syntacticDiagnosticsSync` / `semanticDiagnosticsSync`，每个文件 3–5ms，消息、code、source 和推送的一致，可以直接与推送得到的基线比较。基线和写后检查都优先拉取；拉取失败或预设不支持时，退回等待推送。文件已经打开时，改动前先拉一次，拿到的是精确基线。
- **T18：**
  - patch 模式不再逐文件检查：逐文件检查会把"后面的操作才补上的导出"误报为错误。现在先写完所有文件，再按改动前的内容逐个检查（顺序执行，因为每次检查都会在改动前后各拉一次其他文件）。
  - 结果文本按检查器汇总，总数上限 10 条，没查到的文件按名字列出。顶层 `details.lifecycle` 合并了各文件的诊断，卡片无需改动即可显示。
  - deferred 模式（命令式 provider）保持原样。
- **T19 结论：会。** tsserver 改完一个文件后，会重新推送其他已打开文件的诊断。但有了拉取就不必依赖推送时机：写入时，在改动前后各拉一次同一服务器里其他已打开的文件（最多 20 个，最近使用的优先，排除同一次 patch 改到的文件），报告其中新增的错误，标题是 `N errors introduced in other open files`。没有新增时写成 `no new errors (also checked N other open files)`，说明检查范围。只对能拉取的服务器（目前是 TypeScript）生效。
- **T20：**
  - 状态新增 `missing`，条目带 `installHint`。只有声明了 `installHint` 的预设才会报 missing，所以 TypeScript（跟随项目自己的 `typescript`）不会因为普通的 `package.json` 项目被报缺失。
  - 设置页概览里，每个已登记项目根目录缺的服务器也会列出。启动失败（例如 rustup 代理没装组件）的条目同样附带提示。
  - `?refresh=1` 会清掉探测缓存，并让启动失败的服务器重新尝试；设置页打开时自动带上。
  - 共享组件 `components/ui/CopyableCommand`：等宽命令文本，可选中，会换行，带复制按钮。
  - 用本机真实预设核对过：有 `go.mod` 时 gopls 显示 missing 并给出 `go install …`；有 `Cargo.toml` 时 rust-analyzer 因 rustup 报 "Unknown binary" 而失败，并给出 `rustup component add rust-analyzer`。e2e 截图确认了弹窗效果。是否安装了 gopls 因机器而异，所以没有把这一项写进常驻 e2e。
- **测试：**
  - 真服务器集成测试：干净编辑在预算内答复；改签名后，报出另一个已打开文件里的调用错误；patch 先写完再检查。
  - 单测：patch 汇总与未检查文件、其他文件的格式化、missing、redetect、路由概览与 refresh、指示器和设置页的提示与复制。


## P3b：随包附带 pyright

- [x] **T21 打包。** server 增加依赖 `pyright`，固定小版本。`bundle.mjs` 把整个包复制到 `bundle/vendor/pyright/`，连同 LICENSE。新增 `resolveBundledPyright()`：dev 走 node_modules，release 走 vendor，查找方式与 `resolveBundledTypeScriptServer` 一致。预设改为用 sidecar node 启动 `langserver.index.js --stdio`，不再在 PATH 上探测；用户想换成 basedpyright 等，在 P3d 里用同 id 覆盖。
- [x] **T22 配置下发 + venv 识别。**
  - `LaunchSpec` 增加 `settings?: Record<string, unknown>`（按 section 取值）。`client.ts` 处理 `workspace/configuration` 时按 `item.section` 查找，找不到再回 `null`。
  - pyright 预设探测 `<root>/.venv`、`<root>/venv`（Windows 是 `Scripts/python.exe`），找到就下发 `python.pythonPath`。
  - 找不到 venv 时，下发 `python.analysis.diagnosticSeverityOverrides.reportMissingImports = 'warning'`，避免 agent 新加的 import 被当作新增错误。
  - 项目里有 `pyrightconfig.json` 或 `[tool.pyright]` 时以项目配置为准（pyright 本身的优先级就是这样），我们只补 pythonPath。
- [x] **T23 测试。** 单测覆盖 venv 探测和 settings 应答。真服务器集成测试：临时 Python 项目写入类型错误，结果里报出该错误；不建 venv 时加一个找不到的 import，不报为错误。

**P3b 验收：** 在没有装任何 Python 工具的机器上，Pi agent 在 Python 项目里写出类型错误，能收到这个错误；有 `.venv` 的项目里第三方 import 能正常解析。

**P3b 实施记录（2026-10-04，分支 `feat/lsp-p3b`）：**

- **T21：**
  - `pyright@1.1.414` 精确固定。bundle 只复制 `package.json`、`LICENSE.txt`、`langserver.index.js` 和 `dist/`，不含 source map。实际约 18MB、5417 个文件（大部分是 typeshed），按磁盘块计 32MB。
  - 保留 pyright 自己的 `package.json` 很关键：没有它，这些 CommonJS 文件可能被当成 ESM。
  - 用 sidecar node 直接启动 `bundle/vendor/pyright/langserver.index.js` 冒烟通过，能报出类型错误。macOS 打包把整个 `server/bundle/` 复制到 `Resources/server/`，不需要另外配置；pyright 是纯 JS，不影响签名。
  - `resolveBundledTypeScriptServer` 和 `resolveBundledPyright` 共用 `resolveBundledPackageFile`。
- **T22：**
  - `LaunchSpec.settings` 按 section 回答 `workspace/configuration`，带点的 section 会逐层取值。pyright 只请求 `python` 和 `pyright` 两个 section，从 `python` 里读 `pythonPath` 和 `analysis.*`。
  - **坑：** 只要下发了 `analysis` 对象，pyright 就把 `autoSearchPaths` 当作 false（`src/` 布局的导入会解析失败），所以必须显式设为 `true`。
  - 没有 venv 时，`reportMissingImports` 降为 warning。
  - venv 探测和启动参数一起缓存，redetect 时一并清除。venv 是在服务器启动之后才建的，要等服务器重启才生效。
- **T23 实测结论：**
  - pyright 对"空→空"也会推送诊断，所以不需要像 TypeScript 那样拉取；干净编辑能在预算内答复。
  - pyright 不会自己找工作区里的 `.venv`。反向对照：去掉 settings 后，"venv 内的包能解析"和"无 venv 时缺失导入不算错误"两个测试都会失败；加上 settings 后都通过。
  - venv 测试用 `python3 -m venv --without-pip` 建环境，再手写一个包到 site-packages；机器上没有 python3 时跳过。


## P3c：RenameSymbol

- [ ] **T24 manager 计算重命名。**
  - 初始化声明 `workspace.workspaceEdit.documentChanges: true` 和 `resourceOperations: []`，以及 `textDocument.rename.prepareSupport: true`。
  - 新增 `manager.computeRename({ root, file, line, character, newName })`：先从磁盘同步，再调用 `prepareRename`（不能改名时返回 `rename_not_allowed`），再调用 `rename`。
  - 把 `changes` 和 `documentChanges` 两种格式统一成 `{ file, edits[], contentHash }[]`。`contentHash` 取自 DocumentStore 里语言服务器所用的那份内容。
  - 出现资源操作（重命名、新建、删除文件）就整体返回 `unsupported_edit`。
  - 这是 manager 的通用接口，不知道调用方是谁，桌面端以后也能用。
- [ ] **T25 原子多文件写入。**
  - 从 edit-tool :1056-1143 抽出 `commitComputedContent(file, original, updated, options)`，Edit 改为调用它，行为不变。
  - 新增 `applyTextEditsAtomically(fileEdits, options)`：
    1. 用 `runWithFileWriteLocks` 拿到所有文件的锁；
    2. 逐个读磁盘、比对 `contentHash`，任何一个不一致就返回 `stale_content`，不写入；
    3. 在内存里按范围套用编辑（UTF-16 列，从后往前），跑内容校验；
    4. 逐个写入，任何一个失败就用内存原文回滚已写的文件，返回 `apply_failed`；
    5. 每个文件 `recordFileBackup`、`recordRead` + `recordWrite`、生成 diff、运行写后诊断，再用 T18 汇总。
- [ ] **T26 RenameSymbol 工具 + 权限。**
  - 输入：`{ file_path, line, symbol, occurrence?, new_name, preview_only? }`。定位复用 LSPTool 的 `locateSymbol`；`new_name` 要做标识符格式的基本校验。
  - 只有锚点文件对应的服务器支持 `renameProvider` 时才注册，门控方式同 LSPTool。
  - 加入 `EDIT_TOOLS`，调用前对锚点文件按 `fileWrite` 征询。
  - `isSensitiveFile` 下沉到 utils 层。执行中对每个目标路径检查：工作区外（realpath 后）、`external`（依赖库、`lib.d.ts`）、敏感文件。命中任何一个就整体拒绝，结果里列出这些路径，建议改用 Edit。
  - `preview_only` 返回文件列表、每个文件的改动数和 diff，不写盘。
  - 结果格式复用 `perFileResults`，文本头为 `Renamed foo → bar: 12 edits in 5 files`。正确的 rename 应该引入零个错误，所以有新增诊断时，结果里明确提示"可能有名字冲突或遮蔽"。
  - 工具描述写明：只改代码里的语义引用，不改字符串、注释或文件名。
- [ ] **T27 桌面卡片。** `ToolExpandedContent` 把 `RenameSymbol` 映射到 `FileMutationResult`；`toolFormatters` 的摘要显示 `foo → bar · 5 files`。
- [ ] **T28 测试。**
  - 假服务器：两种 WorkspaceEdit 格式、资源操作被拒、`prepareRename` 拒绝。
  - 写入引擎：哈希不一致时什么都不写、写到一半失败能回滚、多字节字符的列号、写后快照可以直接接着用 Edit。
  - 权限：工作区外、依赖库、敏感文件都会整体拒绝；plan 模式下被拦截。
  - 真服务器集成测试：跨三个文件重命名一个导出函数，零新增错误。
  - e2e：模型调用 `RenameSymbol`，磁盘内容和卡片都正确。

**P3c 验收：** 在 zclaudia 仓库里让 Pi agent 重命名一个跨多个文件引用的函数，一次调用完成，结果报零个新错误，卡片能逐文件看 diff 和撤销；plan 模式下这个工具被拦截。

## P3d：配置来源（用户 + 插件）

- [ ] **T29 动态注册表。**
  - 新增 `LanguageServerRegistry`：来源分为 `builtin` / `plugin` / `user`，优先级用户 > 插件 > 内置。id 相同视为覆盖，同一扩展名由优先级高的认领。

  - 状态条目增加 `source`。
- [ ] **T30 用户级自定义服务器。**

## P3e：桌面查看器诊断

- [ ] **T33 server 接口。**
  - `GET /api/language-servers/file-diagnostics?root=&path=`：`root` 必须是已登记的项目根目录或某个会话的 worktree，否则返回 403。
    - 没有该文件可用的服务器：`{ state: 'unavailable' }`。
    - 有，但没有运行中的实例：`{ state: 'not_running' }`，不启动、不持有租约。
    - 正在运行：从磁盘同步，等待稳定推送，预算 1.5s，返回 `{ state: 'ready', diagnostics }`；超时返回 `pending`。
  - `POST /api/language-servers/viewer-leases { root }` → `{ leaseId }`，TTL 90s；`POST …/:id/renew`、`DELETE …/:id`。TTL 到期自动释放，防止桌面端崩溃或断网后租约泄漏。root 校验同上。
- [ ] **T34 查看器标记。**
  - 只改主查看器 `FileViewerPanel`。`CodeRow` 在有诊断的行显示行号旁圆点（错误用 destructive，警告用 warning）和整行淡底色；悬停或轻点圆点，用 `HoverPopover` 显示该行的诊断。
  - 头部显示 `2 errors · 1 warning`，点击用 `targetLine` 跳到下一处。
  - 状态是 `not_running` 时，头部显示 "Check types" 按钮；点击后获取租约，每 60s 续租，关闭文件或卸载组件时释放。
  - 文件 mtime 变化时重新拉取诊断；服务器正在启动时 2s 轮询。远程 backend 走 `apiCallForBackend`。
  - 遵守 `docs/ui-conventions.md`，界面文案用英文。
- [ ] **T35 测试。** 路由：root 校验、`not_running` 不启动、租约 TTL 到期释放。桌面端：标记渲染、悬停内容、跳到下一处、按钮获取租约及卸载时释放。e2e：打开一个有错误的文件，点 Check types 后显示标记。

## 风险

- **跨文件诊断的覆盖面。** T19 只能检查已打开的文件。改签名弄坏的调用方如果没被打开过，就查不到。结果文本必须写明检查范围，不能让模型误以为"没有错误"。
- **pyright 的噪音。** 没有 venv 的项目里，第三方类型都是 Unknown，可能产生其他类型的新增错误（例如属性访问）。T23 实测后再决定要不要降级更多规则。
- **pyright 内存。** 大型 Python 仓库里可能占几百 MB，受全局 3 个进程上限约束。
- **rename 期间的并发写入。** 哈希校验只能防住"算完到写入之间"被改的情况；写入过程中外部进程又写同一文件，仍然可能被覆盖。这和 Edit 现有的风险相同，不额外处理。
- **注册表变化打断 run。** 用户在 run 期间修改自定义服务器，会停掉正在用的实例，下一次查询要冷启动。可以接受，在设置页说明。
- **插件权限状态缓存。** `provider.register` 只在构造插件上下文时检查一次，这个坑不能照搬。T31 必须每次启动都查 `hasPermission`，并且监听撤销事件。

# Terminal ANSI 16-Color Palette (Light-Mode Readability) — Design

**Date:** 2026-07-03
**Status:** Approved (pending spec review)
**Mockup:** https://claude.ai/code/artifact/d4a67ea4-51c8-4307-8f19-94c493c14788

## Problem

The terminal panel is unreadable in light mode for any colored output (starship prompts,
git diff, npm warnings, `ls` colors):

- `getTerminalTheme()` (`apps/desktop/src/components/terminal/XTerminal.tsx:48-57`) maps only
  four colors from CSS variables: `background`, `foreground`, `cursor`, `selectionBackground`.
- The 16 ANSI palette slots are never set, so xterm.js falls back to its built-in defaults —
  a palette designed for dark backgrounds (yellow `#e5e510` ≈ 1.3:1 against the light
  terminal background `hsl(45 15% 95%)`; cyan `#11a8cd` ≈ 2.8:1; both far below the 4.5:1
  WCAG body-text threshold).
- Dark mode only looks fine by coincidence: the default palette happens to be tuned for
  dark grounds. It still clashes in hue (fluorescent green/cyan) with the warm-charcoal
  neutral axis.

## Goal

Colored terminal output is readable in all five themes, and the terminal palette belongs to
the same color system as the rest of the chrome.

- All 16 ANSI slots become theme tokens generated by the existing token pipeline
  (`apps/desktop/scripts/tokens/config.mjs` → `pnpm gen:tokens` → `index.css`).
- Hues anchor to the existing accent/glyph system: red 4 (destructive), green 150 (success),
  yellow 38–44 (warning), blue 214 (primary), magenta 285 (near glyph-purple),
  cyan 185–190 (near glyph-teal).
- `minimumContrastRatio: 4.5` as a safety net for colors the palette cannot control
  (256-color / truecolor escape sequences emitted directly by programs).

Non-goals:

- No per-theme ANSI overrides beyond the light/dark split (both light themes share one set,
  all three dark themes share one set — same sharing model as the existing accents).
- No user-configurable terminal color schemes.
- No change to `--terminal-bg` / `--terminal-fg` / cursor / selection values.

## Design

### 1. Tokens

Add two literal objects `lightAnsi` / `darkAnsi` to `config.mjs`, spread into
`lightAccents` / `darkAccents` respectively. Token names: `terminal-ansi-<slot>` with
kebab-case bright slots (`terminal-ansi-bright-black`, …). Values (HSL triplets):

| Slot | Light | Dark |
| --- | --- | --- |
| black | `[45, 8, 16]` | `[35, 6, 22]` |
| red | `[4, 66, 45]` | `[4, 60, 62]` |
| green | `[150, 48, 33]` | `[150, 40, 56]` |
| yellow | `[38, 80, 38]` | `[42, 65, 60]` |
| blue | `[214, 70, 45]` | `[214, 62, 64]` |
| magenta | `[285, 45, 48]` | `[285, 45, 68]` |
| cyan | `[190, 65, 32]` | `[185, 45, 56]` |
| white | `[45, 6, 78]` | `[35, 10, 80]` |
| bright-black | `[45, 5, 43]` | `[35, 6, 45]` |
| bright-red | `[4, 70, 52]` | `[4, 65, 68]` |
| bright-green | `[150, 45, 40]` | `[150, 42, 63]` |
| bright-yellow | `[40, 78, 45]` | `[44, 70, 66]` |
| bright-blue | `[214, 70, 56]` | `[214, 65, 70]` |
| bright-magenta | `[285, 50, 58]` | `[285, 50, 74]` |
| bright-cyan | `[190, 60, 40]` | `[185, 50, 63]` |
| bright-white | `[45, 10, 88]` | `[35, 12, 93]` |

Rationale notes:

- Every light-theme slot intended for foreground use meets ≥ 4.5:1 against
  `hsl(45 15% 95%)` (verified in the mockup's live contrast table).
- `white` / `bright-white` stay deliberately light in the light themes: their semantic role
  is background blocks and reverse-video text. When a program uses them as foreground,
  `minimumContrastRatio` darkens them automatically (same mechanism VS Code uses).
- `bright-black` (light) reuses the muted-foreground value `[45, 5, 43]` so dim/comment text
  matches the chrome's muted text.
- Dark values are a low-risk harmonization: same hue set as light, lightness raised into the
  dark-ground readable band (56–74). Close to the xterm defaults in feel, minus the
  fluorescent green/cyan.

### 2. Theme mapping

`getTerminalTheme()` in `XTerminal.tsx` extends its returned `ITheme` with all 16 slots,
reading `--terminal-ansi-*` via the existing `hslToHex` helper:

```ts
black:   get('--terminal-ansi-black'),
red:     get('--terminal-ansi-red'),
// … 16 slots total, through:
brightWhite: get('--terminal-ansi-bright-white'),
```

No lifecycle changes needed — `controller.refreshTheme()` already re-reads the full theme on
theme switches.

### 3. Contrast safety net

`TerminalController.ts` adds `minimumContrastRatio: 4.5` to the `new Terminal({...})`
options. This covers:

- 256-color / truecolor output the palette cannot influence.
- Foreground use of the intentionally-light `white` / `bright-white` slots.
- Any future theme added to the token config without hand-tuned ANSI values.

### 4. Testing

- `XTerminal.test.tsx`: assert the theme object passed to the controller contains all 16
  ANSI fields resolved from the CSS variables, and the existing 4 fields are unchanged.
- `TerminalController.test.ts`: assert the constructed `Terminal` receives
  `minimumContrastRatio: 4.5`.
- Manual smoke pass across the five themes (starship prompt, `git diff`, npm warn output).

## Error handling

`hslToHex` already returns `#000000` for missing/malformed variables. A missing ANSI
variable in a future theme would render that slot black — visible but readable in light
mode, and `minimumContrastRatio` rescues it in dark mode. No additional handling needed.

## Risks

- Programs that hardcode truecolor output tuned for dark terminals will be auto-adjusted by
  `minimumContrastRatio`, which can shift their intended hue slightly. This is the accepted
  trade-off (identical to VS Code's default behavior, ratio 4.5).
- The generated `index.css` blocks grow by 16 lines per theme; no runtime cost beyond the
  existing `getComputedStyle` reads in `getTerminalTheme()`.
